# recovery-links-20261113 — восстановление исторических публичных ссылок

Версионная миграция данных. Восстанавливает из старой базы (дамп Beget,
восстановленный в отдельную database) только **публичные `stream_url` дней
с бизнес-датой строго раньше 2026-11-01**. Это не общее слияние legacy
(`scripts/merge_legacy_streaming.py`) — остальное не трогается.

## Что переносится

- `stream_days.stream_url` для дней с бизнес-датой `< 2026-11-01`
  (бизнес-дата = `start_date + (day_index - 1)`, `day_index` с 1) и непустым
  URL из старой базы.
- Новые исторические события — только если у них есть qualifying-ссылки.
  `id` новых дней — детерминированный UUID5 от версии миграции и id источника;
  коллизия с существующим id — отказ. `server_url` и `stream_key` новых дней —
  пустые строки.
- Длительность нового события обрезается по последнему историческому дню до
  cutoff; будущие дни не создаются.
- `content_url` события — только если событие-источник целиком до cutoff
  (`start_date + duration_days - 1 < 2026-11-01`), даже если назначение
  после обрезки выглядит «целиком до cutoff». На событиях, пересекающих
  cutoff, пропускается; на будущих не меняется. Content_url-only ссылки
  (события без qualifying `stream_url`, но с непустым `content_url` целиком
  до cutoff) восстанавливаются и на matched-событиях, и — если события нет
  в текущей базе — новым событием с явными безопасными метаданными
  (`server_url`/`stream_key` пустые, `created_by_id` по email-remap,
  длительность обрезана по последнему дню до cutoff).

## Что НЕ переносится и не меняется

- Пользователи: вставок нет. `created_by_id` старых событий переназначается
  по уникальному нормализованному непустому email (lower/strip) на текущего
  пользователя; без совпадения — `NULL`. Текущие пользователи, пароли и роли
  не изменяются.
- `server_url`, `stream_key`, блокировки, авторизация, уведомления, сессии,
  назначения, аналитика из старой базы — никогда не импортируются.
- Текущие дни с бизнес-датой `>= 2026-11-01` — не изменяются и не создаются.
- Длительности существующих событий — не изменяются. Исторический день вне
  текущей длительности — конфликт, миграция падает до записи.
- Все прочие текущие поля, включая `updated_at` — без изменений
  (миграция не выполняет `UPDATE` по ним).

## Идентификация событий

1. `ffkm_admin_tournament_id` + совместимая дата начала источника (та же
   дата или внутри окна `[start_date, start_date + duration_days - 1]`
   текущего события) и единственный свободный кандидат; `title` не обязан
   совпадать (переименованное событие с тем же verified tournament ID
   совместимо), но совпадение `title` никогда не перекрывает несовместимую
   дату. Дни сопоставляются по фактической бизнес-дате
   (`start_date + day_index - 1`), а не по переиспользованному `day_index`
   источника. День источника, чья бизнес-дата не помещается в текущую
   длительность события, — явный конфликт, а не молчаливый сдвиг дат.
2. Точный `id`, если идентичность (нормализованный непустой title +
   start_date) подтверждена; пустой title идентичность не доказывает.
3. Нормализованный непустой `title` + `start_date`, если кандидат ровно
   один и verified tournament ID не противоречит (оба либо совпадают,
   либо пусты).

Неоднозначность на любом шаге — исключение до любых записей. Каждая ветка
сопоставления обязана соблюдать one-to-one: два события источника не могут
претендовать на одно текущее событие. Content-only ссылка с совпадающими
tournament/title, но несовместимой датой не перезаписывает чужое текущее
событие: планировщик останавливается до любых записей с конфликтом, когда
`ffkm_admin_tournament_id` уже занят несовместимым событием; перезаписи
нет и отдельной вставки нет.

Предусловие источника: legacy `stream_events` обязан иметь проверенный
уникальный непустой `ffkm_admin_tournament_id` (фактический индекс
восстановленного источника проверен, групп дубликатов — 0); источник без
такого ограничения, где оно не поддерживается или нарушено, использовать
нельзя.

## Запуск

Сухой прогон (по умолчанию; stdout — только счётчики и SHA-256 плана,
без URL и PII):

```bash
cd /opt/streaming/backend
sudo -u streaming .venv/bin/python -m scripts.recovery_links_20261113 \
    --current-url postgresql://streaming@/streaming \
    --legacy-url postgresql://streaming@/streaming_legacy
```

Запись — только с хэшем проверенного сухого прогона:

```bash
sudo -u streaming .venv/bin/python -m scripts.recovery_links_20261113 \
    --current-url postgresql://streaming@/streaming \
    --legacy-url postgresql://streaming@/streaming_legacy \
    --apply --expected-plan-sha256 <sha256 из сухого прогона>
```

Свойства исполнения:

- обе database задаются явно, `.env` не читается;
- источник — согласованный read-only снимок `REPEATABLE READ` (все SELECT-ы
  видят одно состояние, даже если базу трогают параллельно);
- в `--apply` блокировки `ACCESS EXCLUSIVE` (`public.stream_days`,
  `public.stream_events`, `public.users` — в фиксированном порядке) —
  первый запрос транзакции текущей базы, ДО schema-проверок и любых
  SELECT-ов: снимок `REPEATABLE READ` фиксируется первым запросом, и чтение
  до LOCK оставило бы невидимыми коммиты, случившиеся во время ожидания
  блокировки. `users` блокируется тоже: его неизменный прообраз
  (email/password_hash/role) входит в хэш плана и проверяется перед
  коммитом;
- входные SELECT-ы имеют `ORDER BY id`, а хэш плана канонизирует списки
  операций по содержимому: физический порядок строк не влияет на хэш;
- `--apply` пересчитывает план в той же транзакции и сверяет хэш: расхождение
  (drift), неоднозначность или нарушение инвариантов — откат;
- перед коммитом проверяется, что пост-cutoff дни, пользователи
  (email/password_hash/role) и нетаргетные поля событий не изменились;
- вставки/обновления — явные allowlisted операторы, без
  `ON CONFLICT DO NOTHING`; одна атомарная транзакция;
- повторный прогон после успешной записи — нулевые изменения (идемпотентно).

## Предусловия и откат

- Свежий проверенный бэкап БД (`mainstream-backup.service`) **и** каталога
  `uploads/` до любого `--apply`.
- Схема проверяется до построения плана, отдельно для каждого подключения:
  текущая база — полный набор читаемых колонок, включая
  `stream_events.content_url` и fingerprint-поля (`users.password_hash`,
  `users.role`, `stream_events.locked_by_user_id/created_at/updated_at`);
  legacy — только колонки плана (`users.id/email`,
  `stream_events.id/title/start_date/duration_days/ffkm_admin_tournament_id/
  content_url/created_by_id`, `stream_days.*`), fingerprint-поля там не
  требуются. Несоответствие — останов до построения плана.
- Локальный учебный откат: восстановить бэкап в отдельную database и
  прогнать dry-run против неё — счётчики должны дать тот же план, что и
  боевой сухой прогон до записи.
- Миграция не делает авто-отката поверх данных новее снимка: если после
  сухого прогона в текущую базу что-то записали, хэш плана изменится и
  `--apply` откажется записывать. В этом случае — новый сухой прогон,
  пересмотр плана и повторная проверка бэкапа.
